# 벼림 PRD 만들기

HR 담당자가 자기 회사 업무 문제로 도구를 만들기 전에 쓰는 **한 장짜리 설명서(PRD.md)** 를 함께 만든다.
읽는 사람은 개발 경험이 없는 HR 담당자이고, PRD 를 받아 만드는 쪽은 클로드 코드다.
질문과 PRD 모두 HR 업무 말로 쓴다. 기능 목록은 클로드 코드가 「기능 N번만 만들어줘」 한 줄로 받아 끝낼 수 있게 쓴다.

## 지켜야 할 것

- **실데이터를 요청하지 않는다.** 지원자 · 직원 이름, 연락처, 급여 · 평가 · 처우 값, 사내 문서 원문을 붙여 달라고 하지 않는다. 사용자가 붙여 넣으면 「회사 데이터는 넣지 않습니다. 칸 이름만 남기고 값은 가상으로 만들겠습니다」라고 말하고 값을 버린다.
- **지어내지 않는다.** 숫자 · 인용 · 사내 규칙을 사용자가 말하지 않았으면 `[확인 필요]` 로 둔다. 그럴듯한 값을 채우지 않는다.
- **키를 받지 않는다.** API 키 · 비밀번호 · 토큰을 채팅으로 받지 않고 PRD 에 적지 않는다. 사용자가 붙여 넣으면 「키는 채팅에 붙이지 않습니다. 소유자가 Vercel 환경 변수에 직접 넣습니다」라고 말하고 그 값을 어디에도 쓰지 않는다.
- **한 번에 질문 하나.** 질문마다 추천 답과 그 이유 반 줄을 붙인다. 사용자가 「네」라고만 하면 추천 답으로 정한다.
- **찾을 수 있는 것은 묻지 않는다.** 작업 폴더의 `정의.md`, `문제.md`, `범위카드.md`, `sample-data.csv`, `공유.md`, 기존 `PRD.md` 가 있으면 먼저 읽는다. `정의.md` 의 「PRD로 넘기는 칸」에 적힌 칸은 정해진 것으로 본다.
- **정의를 뒤집지 않는다.** `정의.md` 와 다른 형태 · 기능이 낫다고 보면 이유를 붙여 한 번만 묻는다. 사용자가 그대로 가겠다고 하면 다시 꺼내지 않는다.
- 개발 용어(엔드포인트, 스키마, 컴포넌트, 마이그레이션 등)를 질문에 쓰지 않는다. 필요하면 「화면 · 처리 · 기록」 세 부분으로 말한다.

## 순서

### 1. 읽기

작업 폴더에서 `정의.md`(`정의-문답.md` 로 만든 한 문단 정의) · `문제.md`(문제 한 장) · `범위카드.md`(운영진이 나눠 준 카드) · `sample-data.csv` · `공유.md`(운영진 공유 카드와 받은 메모) · 기존 `PRD.md` 를 찾아 읽는다.
하나도 없으면 「어떤 반복 업무의 어떤 불편을 줄이고 싶은지 한두 줄로 알려 주세요」라고 한 번만 묻는다.

### 2. 형태 확인

`정의.md` 에 형태가 있으면 묻지 않는다. 없으면 아래 넷 중 하나를 권하고 이유를 한 줄로 쓴다.

| 형태 | 권하는 경우 |
|---|---|
| 스킬 | AI가 글을 읽고 판단 · 요약 · 초안 작성을 해야 하고, 쓰는 사람이 클로드를 쓸 수 있다 |
| 대시보드(아티팩트) | 표 · 그래프로 보기만 하면 되고, 자료는 사람이 넣어 준다 |
| 로컬 에이전트 | 내 PC 폴더의 파일을 읽어 처리하고, 쓰는 사람이 나 하나다 |
| 웹 서비스 | 여러 사람이 입력하고 같은 기록을 함께 본다 |

### 3. AI 연결 정하기

도구 안에서 AI(클로드)가 글을 읽고 쓰거나 판단해야 하는지 정한다. 형태마다 다르다.

| 형태 | AI 연결 | 묻는가 |
|---|---|---|
| 스킬 | 필요 없다. 클로드가 그 자리에서 읽고 판단한다 | 묻지 않는다 |
| 로컬 에이전트 | 필요 없다. 클로드 코드가 그 자리에서 처리한다 | 묻지 않는다 |
| 대시보드 | 대개 필요 없다. 화면 안에서 AI가 글을 써야 하면 「AI 기능 아티팩트」를 권한다. claude.ai 설정에서 켜고, 키 없이 보는 사람의 클로드 사용량으로 작동한다 | 화면 안에 AI 일이 있을 때만 |
| 웹 서비스 | 아래 세 답 중 하나로 정한다 | 묻는다 |

웹 서비스에서는 「이 도구 안에서 AI가 글을 읽고 쓰거나 판단해야 하나요?」라고 묻고, 셋 중 하나를 추천한다.

| 답 | 뜻 | 권하는 경우 |
|---|---|---|
| ① 연결하지 않음 | 정해 둔 양식 · 규칙으로 화면이 처리한다 | 결과가 「기본 양식 + 입력값으로 날짜 · 항목 채우기」로 만들어질 때 |
| ② 스킬로 따로 | AI 일은 스킬로 떼어 담당자가 클로드에서 하고, 결과를 웹 서비스에 붙여 넣는다 | AI 판단이 가끔 필요하고, 그 일을 하는 사람이 담당자 한 명일 때 |
| ③ Claude API 연결 | 웹 서비스가 서버에서 클로드를 불러 결과를 만든다 | 여러 사람이 버튼 하나로 AI 결과를 받아야 하고, 소유자가 키와 사용 한도를 관리할 수 있을 때 |

**추천 원칙: AI 없이 먼저 돌아가게 한다.** 기능 1번이 ①로 작동하면 ①을 추천하고, AI가 붙는 일은 뒤 순서의 기능으로 따로 뗀다. 사용자가 ③을 고르면 그대로 따른다.

③을 고르면 PRD 3절 「AI 연결」 표의 여섯 줄(어디서 부르나 · 넣는 것 · 받는 것 · 키 보관 · 사용 한도 · 실패할 때)을 채운다. 아래는 사용자가 묻지 않아도 PRD 에 그대로 적는다.

- 키는 소유자 한 사람이 Anthropic Console 에서 만들어 Vercel 환경 변수 `ANTHROPIC_API_KEY` 에만 넣는다. 코드 · 화면 · GitHub · 채팅에 키를 붙이지 않는다.
- 클로드는 브라우저에서 바로 부르지 않고 Vercel 서버 쪽(서버 함수)에서만 부른다. 브라우저에서 부르면 키가 화면 코드에 드러난다.
- 월 사용 한도를 Anthropic Console 에서 정한다. 금액은 `[확인 필요]` 로 두고 인수인계 메모에 옮긴다.
- AI에 보내는 값은 가상 데이터만이다. 회사 데이터를 AI로 보내는 일은 「오늘 하지 않는 것」에 적는다.
- AI 결과에는 「초안」 표시가 붙고, 사람이 확정하기 전에는 확정 기록으로 저장되지 않는다.
- AI 호출이 실패해도 화면은 멈추지 않는다. 안내 한 줄을 보여 주고 사람이 손으로 쓸 수 있게 둔다.

### 4. 빈칸 묻기

읽은 내용을 `TEMPLATE.md` 의 칸에 맞춰 보고, 채울 수 없는 칸만 묻는다. 아래 순서를 지킨다. 앞 칸이 정해져야 뒤 칸을 물을 수 있다.

| 순서 | 칸 | 질문 예 (추천 답과 함께) |
|---|---|---|
| 1 | 문제 | 「줄이고 싶은 불편은 ○○로 보입니다. 맞나요?」 |
| 2 | 쓰는 사람 | 「매일 쓰는 사람은 채용 담당자 한 명으로 보입니다. 리더도 보나요?」 |
| 3 | 형태 | 2단계 |
| 4 | AI 연결 | 3단계 |
| 5 | 가장 먼저 만들 기능 | 「이것 하나만 있어도 업무에 쓰이는 기능은 ○○입니다. 이것부터 만들까요?」 |
| 6 | 사람이 판단할 자리 | 「결과를 보고 ○○를 정하는 사람은 담당자로 두겠습니다. 맞나요?」 |
| 7 | 팀과 협업 | 「팀 갈래는 역할 나눠 함께, 소유자 한 명이 개발을 맡는 것으로 보입니다. 맞나요?」 (혼자 만들면 「혼자 만들기」로 정하고 넘어간다) |
| 8 | 형태별 칸 | 아래 표 |
| 9 | 오늘 안 할 것 | 「메일 자동 발송과 사내 시스템 연결은 오늘 하지 않겠습니다. 괜찮나요?」 |
| 10 | 성공 기준 | 「○○를 했을 때 ○○가 보이면 성공으로 보겠습니다. 맞나요?」 |

형태별 칸은 PRD 5 · 6절이다. 정한 형태의 줄만 묻는다.

| 형태 | 5절 | 6절 | 질문 예 |
|---|---|---|---|
| 웹 서비스 | 화면 | 기록할 칸 · 누가 읽고 쓰나 | 「표에 남길 칸은 ○ · ○ · ○ 입니다. 리더는 읽기만 하고 고치는 사람은 담당자로 두겠습니다. 맞나요?」 |
| 스킬 | 언제 시키나 · 넣는 자료 | 판단 기준과 결과물 양식 | 「이 스킬이 따를 기준은 ○○입니다. 회사 기준은 항목 이름만 적겠습니다. 결과는 ○○ 표 한 장으로 낼까요?」 |
| 대시보드 | 보여 줄 것 | 넣는 자료의 칸 | 「리더가 가장 먼저 볼 숫자는 ○○입니다. 자료는 담당자가 매주 CSV로 다시 올리는 것으로 두겠습니다. 맞나요?」 |
| 로컬 에이전트 | 읽고 내는 것 | 처리 순서와 실행 방법 | 「읽을 파일은 ○○ 폴더의 ○○입니다. 결과는 ○○ 폴더에 새 파일로 두고 원본은 건드리지 않겠습니다. 맞나요?」 |

질문은 **최대 9개**다. 팀과 협업은 `공유.md` 카드 ①에 있으면 묻지 않는다.

### 5. 기능 나누기

PRD 에서 가장 공들일 곳이다. 클로드 코드는 기능 하나를 새 세션 하나에서 받아 계획 → 만들기 → 확인까지 끝낸다. 아래 규칙대로 나눈다.

1. **세로로 자른다.** 기능 하나는 사람이 화면(스킬은 시키는 말)에서 시작해 결과를 눈으로 볼 때까지 끝까지 이어진다. 「표 만들기」 「화면 만들기」 「디자인 다듬기」처럼 한 겹만 하는 기능은 만들지 않는다.
2. **기능 1번은 가장 얇게.** 가상 데이터로 한 사람이 한 번 써 볼 수 있으면 된다. 웹 서비스의 기능 1번은 저장 없이 가상 데이터를 화면에 넣어 두고 빌드 1에서 첫 배포까지 간다. 「새로 고침해도 남는다」(Supabase 저장 연결)는 기능 2번으로 뗀다.
3. **새 세션 하나 크기.** 30~40분에 끝날 크기로 자른다. 확인 기준이 세 줄을 넘거나 기능 이름에 「와 · 그리고」가 들어가면 둘로 나눈다.
4. **따로 떼는 것.** 아래 일은 다른 기능에 섞지 않고 각각 기능 하나로 둔다.
   - 기록에 칸이 더해지는 일 (웹 서비스는 표를 먼저 바꾸고 화면을 나중에 바꾼다)
   - AI 연결 (3단계 ③일 때. AI 없이 돌아가는 기능 뒤에 둔다)
   - 로그인 · 사람별 권한
   - 메일 · 알림처럼 다른 사람에게 보내는 일
5. **먼저 끝나야 할 기능을 적는다.** 기능마다 그 기능을 시작하기 전에 끝나 있어야 하는 기능 번호를 적는다. 없으면 「없음」.
6. **시간표에 놓는다.** 「빌드 1」(10:15~11:40)은 기능 1번과 첫 배포, 「빌드 2」(13:00~14:40)는 기능 2~3개, 「빌드 3」(15:00~16:30)은 리뷰에서 나온 것 하나까지다. 그 밖은 「나중에」로 둔다. 오늘 할 기능은 다섯 개를 넘기지 않는다.
7. **확인 기준은 눈으로 보는 문장.** 기능마다 가상 데이터로 확인할 수 있는 체크 문장 2~3개를 쓴다. 「잘 된다 · 편하다 · 깔끔하다」는 기준이 아니다.
8. **사람이 판단할 자리를 기능에 묶는다.** 7절의 판단 자리가 걸린 기능은 확인 기준에 「사람이 ○○하기 전에는 ○○되지 않는다」 한 줄을 넣는다.
9. **로그인 없이 할 수 있는 것과 없는 것을 나눈다.** 로그인이 「나중에」면 「리더는 자기 팀만」 같은 접근 제한은 오늘 기록 단계에서 강제할 수 없다. 6절 「오늘」 줄에 「화면 전환으로 보이는 범위만 나누고, 기록은 공개 키로 읽고 쓴다」고 적는다. 실제 접근 제한은 로그인 기능에 묶는다.
10. **협업 갈래에 맞춰 맡은 사람을 적는다.** 기능마다 맡은 사람을 역할로 적는다(소유자 · 팀원 A · 데이터 담당). 사람 이름은 쓰지 않는다.
    - 혼자 만들기 · 역할 나눠 함께: 모든 기능을 개발 담당(소유자 · 혼자면 「나」)이 맡는다. 10절에 데이터 · 확인 · 기록 · 발표 준비 역할이 무엇을 하는지 한 줄씩 적는다. 데이터는 가상 데이터와 바탕 자료, 확인은 기능마다 확인 기준대로 써 보기, 기록은 팀이 정한 것 · PRD 상태 칸 · 인수인계 메모, 발표 준비는 리뷰에서 말할 것 · 5분 데모 순서다. 사람이 적으면 기록과 발표 준비를 한 사람이 맡는다.
    - 형태가 웹 서비스가 아니면(스킬 · 대시보드 · 로컬 에이전트) 나눠 합칠 파일이 거의 없으므로 역할 나눠 함께를 권한다.
    - 범위 나눠 각자: 기능 1번 · 기록에 칸이 더해지는 기능 · AI 연결 · 배포는 소유자가 맡는다. 여러 화면이 함께 쓰는 부분(보는 사람 전환 · 메뉴)은 기능 1번에 넣는다. 팀원 기능의 확인 기준은 저장 없이 볼 수 있는 문장으로 쓴다(「새로 고침해도 남는다」는 합칠 때 소유자가 확인한다). 팀원에게 주는 기능은 서로 다른 화면을 고치게 나누고, 같은 화면을 두 사람에게 주지 않는다. 팀원 기능의 「먼저 끝나야 할 기능」은 기능 1번만 둔다. 팀원은 빌드 1 끝에 받은 사본의 가상 데이터로 화면을 만들고, 소유자는 같은 시간에 저장 연결을 만든다. 14:00에 합칠 때 팀원 화면을 저장에 잇는다. 그래서 기록의 칸은 저장 연결 기능에서 한꺼번에 만든다. 「언제」 칸은 합치는 시각을 따른다. 14:00에 합치는 기능은 빌드 2, 15:30에 합치는 기능은 빌드 3이다.
    - 함께 · GitHub: 기능 하나가 브랜치 하나 · 합치기 요청(PR) 하나다. 기록에 칸이 더해지는 기능은 PR 본문에 「소유자 할 일」로 남기게 적는다. 팀원 기능의 「먼저 끝나야 할 기능」은 기능 1번만 둔다. 여러 화면이 함께 쓰는 부분은 기능 1번에 넣는다. AI 연결과 배포는 소유자가 맡는다. 배포는 소유자 PC 에서 Vercel 커넥터로 하고, 확인은 합친 뒤 배포 주소에서 한다.
11. **파일 이름 · 코드는 쓰지 않는다.** 어떤 파일을 어떻게 만들지는 클로드 코드가 계획 모드에서 정한다. PRD 는 「누가 무엇을 하면 무엇이 보이는가」까지만 쓴다.

### 6. 정리 확인

PRD를 쓰기 전에 정한 내용을 다섯 줄로 보여 주고 「이대로 PRD.md 를 쓸까요?」라고 묻는다.

1. 형태와 AI 연결
2. 기능 1번과 그 확인 기준 한 줄
3. 오늘 할 기능 이름 (빌드 1 · 2 · 3)
4. 사람이 판단할 자리
5. 남은 `[확인 필요]` 개수

고칠 점이 있으면 그 칸만 다시 묻는다.

### 7. PRD.md 쓰기

`TEMPLATE.md` 의 칸 그대로 작업 폴더에 `PRD.md` 를 쓴다. 5 · 6절은 정한 형태의 갈래만 남기고 나머지 갈래와 `<!-- -->` 안내는 지운다. 3절 AI 연결 표는 ③일 때만 남긴다.
같은 폴더에 `EXAMPLE.md` 가 있으면 예시로 본다.

### 8. 쓴 뒤 점검

다 쓴 `PRD.md` 를 다시 읽고 아래를 확인한다. 걸리는 것은 고친 뒤 다음 단계로 간다. 고친 것은 한 줄로 알린다.

- [ ] 기능 1번 하나만 끝나도 업무에 쓰인다
- [ ] 모든 기능이 세로로 잘렸다 (한 겹만 하는 기능이 없다)
- [ ] 기능마다 확인 기준 2~3개와 「먼저 끝나야 할 기능」이 있다
- [ ] 오늘 할 기능이 다섯 개 이하이고 빌드 1 · 2 · 3에 놓였다
- [ ] 7절 「사람이 판단할 자리」가 비어 있지 않고, 걸린 기능의 확인 기준에 들어가 있다
- [ ] 3절 AI 연결이 정해져 있다. ③이면 표 여섯 줄이 다 있고 키 값은 어디에도 없다
- [ ] 10절 「팀과 협업」이 채워졌고, 기능마다 맡은 사람이 역할로 적혀 있다. 범위 나눠 각자면 같은 화면을 두 사람이 맡지 않는다
- [ ] (웹 서비스) 로그인이 「나중에」면 6절 「오늘」 줄에 기록이 공개 키로 읽고 쓰인다는 것이 적혀 있다
- [ ] 6절과 예시 값에 실데이터처럼 보이는 이름 · 연락처 · 금액이 없다
- [ ] 「남은 확인 필요」에 `[확인 필요]` 위치가 모두 모였다

### 9. 다음 할 일 안내

쓴 뒤에 아래 줄만 말한다.

- 「새 세션을 열고 계획 모드에서 `@PRD.md 의 기능 1번만 만들어줘. 다른 기능은 건드리지 말 것.` 이라고 시키세요.」
- 「가상 데이터가 필요하면 `PRD.md 의 6절 칸으로 가상 데이터 20줄 만들어서 sample-data.csv 로 저장해줘` 라고 시키세요.」
- 「기능 하나가 확인 기준을 다 통과하면 `PRD.md 의 기능 1번 상태를 완료로 바꾸고 커밋해줘` 라고 시키세요.」
- 「지금 `@진행-공유.md 를 읽고 공유 카드 ②를 만들어줘` 라고 시켜 운영진에게 PRD 를 알리세요.」
- (AI 연결 ③일 때만) 「AI 연결 기능 차례가 오면 운영진에게 받은 키를 소유자가 Vercel 환경 변수에 넣은 뒤(가이드 4-5), 새 세션에서 `@API연결.md 를 읽고 @PRD.md 의 기능 [번호]번만 만들어줘` 라고 시키세요. 키는 채팅에 붙이지 않습니다.」

## 출처

질문을 하나씩 추천 답과 함께 묻고, 찾을 수 있는 것은 묻지 않고, 정리를 확인받은 뒤 쓰는 방식은 Matt Pocock 의 `grill-me` · `grilling` 스킬(MIT, github.com/mattpocock/skills)에서 가져왔다. 기능을 세로로 자르고 새 세션 하나 크기로 맞추고 「먼저 끝나야 할 기능」을 적는 규칙은 같은 저장소의 `to-tickets` 스킬(tracer-bullet 티켓 · blocking edge)을 참고했다. 발견 질문 목록과 「범위 밖」 칸은 jamesrochabrun 의 `prd-generator` 를, 인용을 지어내지 않고 빈칸으로 두는 규칙은 Enterpret 의 PRD 스킬 가이드를 참고했다. 키 없이 작동하는 AI 기능 아티팩트는 Anthropic 지원 문서 「Prototype AI-powered apps with Claude artifacts」를 따랐다. 문장과 칸은 벼림 담금질 1기에 맞춰 새로 썼다.
